# 알림용 이벤트는 보관·replay하지 않는다

Workbench 이벤트는 **상태 복원용**(예: run 이벤트 — 순서대로 적용하면 화면 상태가 복원된다)과 **알림용**(예: worktree 변경 — "다시 조회하라"는 신호일 뿐 본문이 상태가 아니다)으로 나눈다. 알림용 이벤트는 journal에 보관하지 않고, 구독이 시작된 뒤 발생한 것만 전달한다. 놓친 알림은 복원하지 않으며, 클라이언트는 구독을 시작할 때 대상을 다시 조회한다(오늘 worktree 화면의 동작).

## Considered Options

- 모든 이벤트를 같은 규칙으로 보관·replay — 계약은 균일하지만 파일 변경처럼 초당 여러 건 나올 수 있는 알림이 journal 한도를 소모하고, 재연결 시 이미 무의미한 알림을 대량으로 재전송한다.

## Consequences

- 이벤트 스키마마다 분류(상태 복원용/알림용)를 계약에 둔다. 알림용 스트림의 cursor는 순번 연속성 판단에 쓰지 않는다.
- 2b에서 orchestration·exchange 이벤트를 발행으로 전환할 때 각각의 분류를 이 규칙으로 정한다.
