# Feature Specification: Markdown 목록 렌더링 순서 보존

**Feature Branch**: `033-markdown-rendering-quality`

**Created**: 2026-07-28

**Status**: Draft

**Input**: User description: "MarkdownViewer 최상위 목록 렌더링 순서 버그 수정: 문서 내 서로 떨어진 여러 최상위 목록이 하나로 병합되고 그 사이 콘텐츠보다 앞에 렌더되는 문제를 고쳐 문서 순서를 보존한다"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 제목·문단으로 구분된 여러 목록을 원문 순서대로 본다 (Priority: P1)

사용자는 Markdown 미리보기(AW의 Markdown/SpecKit 탭, markdown-annotator)에서 문서를
읽을 때, 원문에 작성한 순서 그대로 콘텐츠가 표시되기를 기대한다. `spec.md`,
`tasks.md`, `plan.md`처럼 "제목 → 목록 → 제목 → 목록"이 반복되는 문서에서 각 목록은
자신이 속한 제목 아래에, 원문 위치에 그대로 표시되어야 한다.

**Why this priority**: 문서 순서가 뒤바뀌면 미리보기가 원문을 잘못 표현해 읽기·검토·주석
작업이 모두 신뢰를 잃는다. 이 기능(033)의 주 대상 문서가 정확히 이 구조이므로, 순서
보존은 렌더링 품질의 최소 정확성 요건이다.

**Independent Test**: 최상위 목록이 중간 콘텐츠(제목/문단/코드/표/인용)로 분리된 문서를
렌더한 뒤, 렌더 결과의 콘텐츠 순서가 원문 블록 순서와 일치하는지 확인하는 것만으로
독립 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** `- Apple`, 빈 줄, `Middle paragraph`, 빈 줄, `- Banana` 순서의 문서,
   **When** 미리보기를 렌더하면,
   **Then** 화면 순서는 Apple → Middle paragraph → Banana 이고, Apple과 Banana는
   서로 다른 목록으로 표시된다.
2. **Given** `## Setup` 아래 목록, `## Usage` 아래 목록으로 구성된 문서,
   **When** 미리보기를 렌더하면,
   **Then** 각 목록 항목은 자신의 제목 뒤에 나타나며, Usage 제목이 Usage 목록 항목보다
   앞에 온다.
3. **Given** 인접한(사이에 다른 블록이 없는) 여러 목록 항목,
   **When** 미리보기를 렌더하면,
   **Then** 하나의 연속된 목록으로 묶여 표시된다(현재 동작 유지).

### User Story 2 - 순서/비순서 목록 경계와 중첩이 유지된다 (Priority: P2)

사용자는 비순서 목록과 순서 목록이 섞이거나 중첩된 문서에서도, 각 목록의 종류·시작
번호·중첩 관계가 원문 의미대로 표시되기를 기대한다.

**Why this priority**: 순서 보존을 고치는 과정에서 기존에 정상 동작하던 중첩·목록 종류
구분이 깨지면 안 된다. 회귀 방지를 위해 명시적으로 요구한다.

**Independent Test**: 비순서→순서 전환, 시작 번호 지정, 2단계 이상 중첩을 포함한 문서를
렌더해 종류·시작 번호·중첩 계층이 유지되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 비순서 목록 다음에 시작 번호 3인 순서 목록,
   **When** 렌더하면,
   **Then** 비순서 목록과 순서 목록이 각각 별도의 목록으로, 순서 목록은 3부터 표시된다.
2. **Given** 부모 항목 아래 중첩된 자식 목록과, 그 아래 이어지는 최상위 형제 항목
   (예: 부모 A → 자식 A1 → 형제 B),
   **When** 렌더하면,
   **Then** A1은 A 안에 중첩되고, A와 B는 **하나의 목록**으로 유지되며 순서(A→B)가
   보존된다(중첩 항목이 사이에 있다는 이유로 두 개의 목록으로 쪼개지지 않는다).

### Edge Cases

- 문서가 목록으로 시작하거나 목록으로 끝나는 경우 순서가 유지되는가?
- 같은 종류(둘 다 비순서)의 목록이 중간 콘텐츠(제목·문단 등)로 분리된 경우, 하나로
  병합되지 않고 각각 별도 목록으로 유지되는가?
- 중첩 항목이 두 최상위 항목 사이에 위치할 때, 두 최상위 항목이 잘못 분리되지 않고
  같은 목록으로 유지되는가?
- 목록 항목에 부여된 블록/부분 선택 주석이 순서 보존 후에도 올바른 항목에 연결되는가?
- 목록 항목 사이/앞뒤에 삽입된 TaskSummary 등 파생 표시가 올바른 위치에 남는가?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 미리보기는 모든 블록을 원문 문서 순서대로 표시해야 하며, 어떤 블록도
  원문상 자신보다 앞에 있는 콘텐츠보다 먼저 표시되어서는 안 된다.
- **FR-002**: 중간에 목록이 아닌 블록(제목·문단·코드·표·인용·구분선 등)으로 분리된 두
  최상위 목록은 하나의 목록으로 병합되어서는 안 되며, 각각 독립된 목록으로 표시되어야
  한다.
- **FR-003**: 사이에 목록 항목이 아닌 다른 블록(제목·문단·코드·표·인용·구분선)이 없는
  연속된 최상위 목록 항목은 하나의 연속된 목록으로 묶여 표시되어야 한다. 중첩된 하위
  항목이 두 최상위 항목 사이에 있어도 두 항목은 같은 목록으로 유지되어야 한다.
- **FR-004**: 목록 종류(순서/비순서)와 순서 목록의 시작 번호는 원문 의미대로 유지되어야
  하며, 종류가 바뀌는 지점에서 목록이 분리되어야 한다.
- **FR-005**: 중첩 목록의 부모-자식 관계와 중첩 깊이는 순서 보존 수정 이후에도 유지되어야
  한다.
- **FR-006**: 목록 항목에 연결된 주석(블록/부분 선택/삭제/노트)은 순서 보존 이후에도 원래
  대상 항목에 정확히 연결되어야 한다.
- **FR-007**: 회귀 방지를 위해 다음 시나리오를 자동화 테스트로 고정해야 한다: 문단으로
  분리된 목록, 제목으로 구분된 목록, 순서/비순서 전환, 중첩 항목이 두 최상위 항목 사이에
  있는 경우(같은 목록 유지), 목록 항목 주석 유지.
- **FR-008**: 목록 항목은 마커를 **하나만** 표시해야 한다. 네이티브 목록 마커와 커스텀
  마커가 함께 나타나 `• -`(비순서)나 `1. 1.`(순서)처럼 중복되어서는 안 된다.
- **FR-009**: 순서 목록의 표시 번호는 시작 번호에서 항목마다 1씩 증가해야 한다(모든
  항목에 시작 번호가 반복되지 않는다). 작업 항목은 체크박스 마커로 표시한다.

### Key Entities *(include if feature involves data)*

- **RenderedDocumentBlock(목록 항목)**: 원문에서 유도된 의미 블록. 순서(order),
  목록 종류(ordered), 시작 번호(orderedStart), 부모 관계(parentId)를 가진다. 순서 보존은
  블록의 **문서 내 순서(order = 배열 위치)**만을 렌더 순서의 기준으로 삼는다.

## Constitution Alignment *(mandatory)*

- **Monorepo boundary**: `packages/markdown-annotation-react`(MarkdownViewer)가 주
  변경 대상이며, 소비 앱은 `apps/markdown-annotator`(MA)와 `apps/agentic-workbench`(AW)
  이다. **두 앱 모두 이 공유 `MarkdownViewer`를 그대로 사용**하므로 한 번의 수정이 양쪽에
  적용되며, 양쪽 모두 검증한다. 순서 보존은 렌더러 계층 문제이므로 core 변경은 불필요.
- **Frontend layering**: 변경은 `packages/*`의 공유 React 렌더러(shared UI)에 위치한다.
  앱 레이어 변경은 없다.
- **Backend boundary**: N/A (Tauri/Rust 변경 없음).
- **Shared core vs UI**: 공유 UI(MarkdownViewer) 내부의 목록 그룹화·렌더 순서 로직만
  수정한다. core의 블록 모델(order/parentId/sourceRange)은 그대로 소비한다.
- **Persistence and safety**: 파일·세션·권한 변경 없음. 주석 앵커가 올바른 블록에
  유지되는지(안전망)만 검증한다.
- **Documentation and Storybook**: MA(`apps/markdown-annotator`)에 분리된 목록 순서를
  보여주는 Storybook 사례를 추가하고 MA build-storybook으로 검증한다.
  `docs/markdown-rendering-quality.md`에 순서 보존 규칙을 반영한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 최상위 목록이 중간 콘텐츠로 분리된 문서에서 렌더 결과의 콘텐츠 순서가
  원문 블록 순서와 100% 일치한다.
- **SC-002**: "제목으로 구분된 목록", "문단으로 구분된 목록" 두 시나리오에 대한 회귀
  테스트가 추가되고 통과한다.
- **SC-003**: 기존 core 87개, react 86개 테스트가 모두 계속 통과한다(기존 동작 무손상).
- **SC-004**: 순서/비순서 전환, 시작 번호, 중첩 관계를 검증하는 기존·신규 테스트가 모두
  통과한다.
- **SC-005**: 목록 항목에 마커가 중복 표시되지 않으며(비순서 단일 `-`/•, 순서 단일 증가
  번호), 순서 목록 번호가 항목마다 1씩 증가한다. MK-1~3으로 검증한다.

## Assumptions

- 순서 오류의 원인은 렌더러(MarkdownViewer)가 최상위 목록을 문서 전체 단위로 모아 첫
  목록 항목 위치에서 렌더하기 때문이며, core 파서의 블록 순서(order)와 부모 관계는
  올바르다고 가정한다(실제 파서 출력으로 확인).
- 이 수정은 033 브랜치(현재 PR #166)의 후속 수정으로, 별도 신규 브랜치 없이 동일 브랜치에
  포함한다.
- 목록 항목의 블록 id와 parentId 체계는 현재 core 구현을 그대로 사용한다.

### 범위 밖(Out of Scope)

- 한 목록 항목 안에서 문단으로 분리된 여러 하위 목록을 별개 하위 목록으로 보존하는 것은
  범위 밖이다. 현재 파서(033)는 항목 사이 문단을 부모 항목 본문으로 병합하고 하위 목록을
  합친다. 본 수정은 **최상위 목록의 문서 순서 보존**에 한정하며, 이 하위 목록 병합 동작은
  변경하지 않는다.
