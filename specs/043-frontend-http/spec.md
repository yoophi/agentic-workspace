# Feature Specification: 데스크톱 화면을 Workbench 네트워크 경로로 전환 (043, 4단계)

**Feature Branch**: `043-frontend-http`

**Created**: 2026-09-27

**Status**: Draft

**Input**: User description: "043 frontend-http (AW 서버-클라이언트 전환 4단계): AW 프런트엔드의 서버 소유 호출을 Tauri 호환 command에서 042 운영 HTTP/WS 어댑터로 옮긴다. `packages/workbench-client`에 계약 기반 타입 클라이언트(호출, handshake, 1회용 표 → 이벤트 구독, hello=구독 준비, 재연결 = 새 표 + 마지막 cursor, gap 처리)를 운영 코드로 완성하고, 데스크톱은 짧은 토큰(창 출처 묶음, 만료 전 갱신)으로 연결한다. run·교환·orchestration·worktree 이벤트를 네이티브 삽입 경로 대신 구독으로 받고, 화면 동작·오류 문구는 오늘과 같다. 데스크톱 표현 상태는 Tauri에 남는다. 연결 끊김·서버 재기동(새 세대) 때 재연결·재조회 규칙과 오프라인 표시를 정한다. compat command와 네이티브 전달은 아직 지우지 않는다(8단계)."

## 배경

042에서 Workbench는 데스크톱 앱 안에서 루프백 네트워크 끝점으로 열렸지만, 화면은 여전히 앱 내부 호출(창 label로 소유를 정하는 호환 경로)과 앱이 창에 직접 넣는 이벤트로 동작한다. 이 단계는 화면이 **네트워크 경로의 클라이언트**가 되게 한다. 그래야 5단계에서 서버를 별도 프로세스로 떼어 내도 화면을 바꾸지 않고, 8단계에서 호환 경로를 지울 수 있다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 화면의 서버 호출이 네트워크 경로를 거친다 (Priority: P1)

사용자는 오늘처럼 프로젝트를 만들고, 저장한 prompt·목표·실행 설정을 고치고, Worktree 변경·Git 기록·파일을 보고, agent run을 시작하고 prompt를 보내고, 권한 요청에 답하고, agent 사이 교환과 orchestration을 조작한다. 이 모든 서버 소유 조회·변경이 네트워크 경로(Workbench 호출)를 거치며, 화면에 보이는 결과와 오류 문구는 오늘과 같다.

**Why this priority**: 화면이 네트워크 경로만으로 동작해야 서버를 떼어 낼 수 있다. 이것만 되어도 5단계의 전제가 선다.

**Independent Test**: 네트워크 경로로 연결한 창에서 서버 소유 조회·변경을 모두 실행하고, 같은 입력을 호환 경로로 실행한 결과·오류 문구와 비교한다. 서버 소유 호출 중 호환 경로를 쓰는 것이 0개인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 연결된 창, **When** 프로젝트를 만들고 목록을 다시 연다, **Then** 새 프로젝트가 보이고 결과·오류 문구가 오늘과 같다.
2. **Given** 연결된 세션 창, **When** agent run을 시작하고 prompt를 보낸다, **Then** run이 이 창의 작업대 소유로 시작되고 출력이 오늘처럼 보인다.
3. **Given** 잘못된 입력(빈 이름 등), **When** 저장한다, **Then** 오늘과 같은 오류 문구가 보인다.
4. **Given** 한 창이 연 작업대, **When** 다른 창의 자격 증명으로 그 작업대의 run을 조작하려 한다(작업대 id를 직접 넣어도), **Then** 서버의 권한·작업대 소유 판정으로 거절된다. 격리는 화면이 대상을 고르는 방식이 아니라 서버 판정으로 입증한다.

### User Story 2 - 이벤트를 구독으로 받는다 (Priority: P1)

사용자는 오늘처럼 run 출력·권한 요청·run 종료, agent 교환 요청과 상태, 창 제목 요청, orchestration 작업 영역·명령·알림 갱신, Worktree 파일·Git 변경 알림을 실시간으로 본다. 이 이벤트는 앱이 창에 넣는 경로 대신 네트워크 구독으로 도착하며, 같은 이벤트가 두 번 보이거나 빠지지 않는다.

**Why this priority**: 호출만 옮기고 이벤트를 앱 내부 경로로 받으면 서버를 떼어 낼 수 없다. run 출력은 핵심 화면이다.

**Independent Test**: 구독으로 연결한 창에서 run을 돌려 출력·권한·종료를 받고, 교환·제목·orchestration·Worktree 변경을 일으켜 각각 한 번씩 보이는지 확인한다. 같은 창에 앱 내부 전달이 동시에 오지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 실행 중인 run, **When** agent가 출력과 권한 요청을 낸다, **Then** 창에 순서대로 한 번씩 보인다.
2. **Given** 창을 새로 열어 기존 run에 붙는다, **When** 구독을 시작한다, **Then** 이미 지난 출력을 이어 받고(재생) 그 뒤 실시간 출력이 빈틈·중복 없이 이어진다.
3. **Given** 구독 중인 창, **When** Worktree 파일이 바뀐다, **Then** 변경 알림이 한 번 도착하고 화면이 갱신된다.
4. **Given** 구독으로 받는 창, **When** 같은 이벤트가 발생한다, **Then** 앱 내부 전달로도 한 번 더 오지 않는다.

### User Story 3 - 연결이 끊기거나 서버가 다시 뜨면 스스로 회복한다 (Priority: P2)

연결이 끊기면(서버 종료·일시 오류·토큰 만료) 화면은 사용자에게 연결 상태를 보여 주고, 자동으로 다시 연결해 **화면에 이미 반영한 지점**부터 이어 받는다. 이어 받을 수 없으면(보관 한도 초과, 서버 재기동으로 새 세대) 해당 화면 상태를 다시 조회해 맞춘다. 변경 조작은 두 경우를 구분해 알린다 — 보내기 전에 연결이 없으면 "적용되지 않음", 보낸 뒤 응답을 잃으면 "적용 여부 불명"(같은 요청 재시도로 확인).

**Why this priority**: 네트워크 경로는 끊길 수 있다. 5단계(서버 분리)에서 이것이 없으면 화면이 멈춘다. 다만 4단계에서는 서버가 앱 안에 있어 끊김이 드물다.

**Independent Test**: 구독을 강제로 끊고(서버가 연결을 닫음) 자동 재연결 뒤 빠진 이벤트 없이 이어지는지, 이어 받을 수 없는 경우 재조회로 화면이 맞춰지는지, 서버 세대가 바뀐 경우 전체 재조회가 일어나는지 시험한다. 토큰 만료 전에 갱신되어 사용 중 인증 실패가 없는지 확인한다.

**Acceptance Scenarios**:

1. **Given** run 출력을 구독 중인 창, **When** 연결이 끊겼다가 돌아온다, **Then** 끊긴 동안의 출력을 빠짐없이 받고 중복은 없다.
2. **Given** 이어 받을 수 없는 구독(보관 한도 초과), **When** 서버가 이어 받기 불가를 알린다, **Then** 화면은 그 대상을 다시 조회해 현재 상태로 맞춘다.
3. **Given** 서버가 새 세대로 다시 떴다, **When** 창이 다시 연결한다, **Then** 이전 세대의 작업대·run은 없는 것으로 보이고 화면은 오늘 앱 재기동과 같은 상태로 다시 조회된다.
4. **Given** 오래 열린 창, **When** 연결 자격 증명이 만료될 때가 된다, **Then** 사용자 조작 없이 갱신되어 호출·구독이 끊기지 않는다.
5. **Given** 연결이 없는 상태, **When** 사용자가 변경 조작을 한다, **Then** 요청을 보내지 않고 "적용되지 않음"을 알리며, 연결이 돌아오면 사용자가 다시 할 수 있다.
6. **Given** 변경 요청을 보낸 뒤 응답 전에 연결이 끊김, **When** 연결이 같은 서버 세대로 돌아온다, **Then** 같은 멱등성 키로 한 번 재시도해 저장된 결과를 받는다(두 번 적용 없음). 확인할 수 없으면 "적용 여부 불명"을 알린다.
7. **Given** 변경 요청의 응답을 잃은 뒤 서버가 새 세대로 다시 떴다, **When** 다시 연결한다, **Then** 그 변경을 자동으로 다시 보내지 않고 "적용 여부 불명"을 알리며 화면 상태를 다시 조회한다.
8. **Given** 구독 대상의 이벤트를 받았지만 화면에 반영하기 전에 연결이 끊김(또는 화면의 수신자가 교체되는 중), **When** 다시 연결한다, **Then** 반영하지 못한 이벤트부터 다시 받는다(유실 없음, 반영한 것은 중복 없음).

### User Story 4 - 창과 작업대의 수명이 오늘과 같다 (Priority: P3)

세션 창은 오늘처럼 자기 작업대를 가지고, 창을 닫으면 그 작업대의 run이 끝난다(오늘 규칙). 메인·설정 창처럼 작업대가 없는 창은 작업대 없이 동작한다. 여러 세션 창이 동시에 열려도 서로의 run·교환·이벤트를 받지 않는다.

**Why this priority**: 화면이 작업대를 직접 다루게 되므로 오늘 수명 규칙이 깨지지 않게 고정해야 한다.

**Independent Test**: 세션 창 둘을 열어 각각 run을 돌리고, 이벤트가 섞이지 않는지, 한 창을 닫으면 그 창의 run만 끝나는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 세션 창 두 개, **When** 각 창에서 run을 돌린다, **Then** 각 창은 자기 run의 이벤트만 받는다.
2. **Given** run이 돌고 있는 세션 창, **When** 창을 닫는다, **Then** 그 창의 run은 오늘처럼 끝나고 다른 창은 영향이 없다.

---

### User Story 5 - 네트워크 경로를 쓸 수 없으면 오늘 경로로 동작한다 (Priority: P3)

네트워크 끝점이 뜨지 못했거나(포트·권한 문제) 창이 연결 정보를 받지 못하면, 그 창은 오늘 경로(호환 호출·앱 내부 전달)로 동작하고, 진단 기록에 이유를 남긴다. 사용자가 할 수 있는 일은 줄지 않는다.

**Why this priority**: 042는 끝점 기동 실패를 허용했다(앱은 계속 동작). 화면이 네트워크 경로에만 기대면 그 경우 앱이 쓸 수 없게 된다. 호환 경로를 지우는 8단계 전까지의 안전장치다.

**Independent Test**: 끝점 기동을 실패시킨 상태로 앱을 띄워 주요 흐름(프로젝트 목록, run 시작·출력)이 오늘 경로로 동작하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 끝점 기동 실패(또는 창이 처음 연결 정보를 받지 못함), **When** 창을 연다, **Then** 창은 처음부터 오늘 경로로 동작하고 이유가 진단 기록에 남는다.
2. **Given** 네트워크 경로로 시작한 창, **When** 나중에 연결이 끊긴다, **Then** 오늘 경로로 자동 전환하지 않고 네트워크 재연결만 시도한다(같은 변경이 두 경로로 두 번 실행되거나 같은 이벤트가 두 경로로 두 번 오는 일이 없다).

---

### Edge Cases

- 구독 시작 직후(준비 신호 전)의 변경: 화면은 준비 신호를 받은 뒤에만 "구독 중"으로 본다(042 계약).
- 한 창에 대상이 많을 때(run 여럿, orchestration, Worktree): 구독 하나에 담을 수 있는 대상 수 한도를 넘지 않게 나누거나 필요한 대상만 구독한다.
- 이어 받을 수 없음을 알리는 사유(없는 스트림, 보관 한도로 지워진 run, 세대 변경, 구독자 지연)마다 화면 동작이 정해져 있다.
- 호출 중 연결이 끊겨 응답을 못 받은 변경: 같은 세대면 같은 멱등성 키로 재시도(042 계약: 진행 중이면 기다리거나 retryable conflict), 새 세대면 자동 재전송 없이 적용 여부 불명.
- 이어 받기 불가 알림 뒤의 재조회: 재조회 결과와 새로 여는 구독 사이 경계에서 변경을 놓치지 않는다(재조회 기준점 이후부터 구독하거나, 구독을 먼저 연 뒤 재조회하고 중복을 거른다).
- 화면의 수신자(구독 이벤트를 받는 화면 부분)가 바뀌는 동안 도착한 이벤트도 유실되지 않는다.
- 창이 닫히는 중에 도착하는 이벤트·응답은 버린다.
- 토큰 갱신 중 동시에 나간 호출: 갱신이 끝날 때까지 기다리거나 새 토큰으로 한 번 재시도한다.
- 개발(`http://localhost:1420`)과 배포(`tauri://localhost`) 출처 모두에서 동작한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 화면의 서버 소유 조회·변경은 모두 Workbench 네트워크 호출을 쓴다. 대상은 호환 command 인벤토리에서 서버 소유로 분류된 항목 전부이며, 데스크톱 표현 상태(모양 설정·창 상태·Worktree 창 배치·창 열기·외부 URL 열기)는 앱 내부 경로에 남는다.
- **FR-002**: 네트워크 호출의 결과와 오류 문구는 같은 입력의 호환 경로 결과와 같다(화면 문구 변경 없음).
- **FR-003**: 공유 클라이언트 패키지는 계약에서 생성한 타입으로 호출·구독을 제공하는 운영 코드다. 한 번 만든 계약 타입이 화면·시험에서 같은 정의를 쓴다.
- **FR-004**: 창은 앱에서 받은 짧은 자격 증명(그 창의 출처에 묶임)으로 연결하고, 만료 전에 갱신한다. 자격 증명·구독 표는 화면 기록·오류 문구에 나타나지 않는다.
- **FR-005**: 세션 창은 자기 작업대의 id를 알아야 한다. 창의 작업대는 오늘처럼 창 수명에 묶이고(창을 닫으면 닫힘), 같은 창이 호출하는 run·교환·orchestration 조작은 그 작업대를 대상으로 한다.
- **FR-005a**: 창 사이 격리는 서버 권한 판정으로 성립한다. 한 창의 자격 증명으로는 다른 창의 작업대·run·교환·orchestration을 조작하거나 구독할 수 없다(작업대 id를 알아도). 오늘 호환 경로가 창 label로 보장하던 격리를 네트워크 경로에서도 같은 수준으로 유지한다.
- **FR-006**: 이벤트(run, 교환, 작업대 알림, orchestration, Worktree)는 1회용 표로 연 구독으로 받는다. 화면은 준비 신호를 받은 뒤를 구독 시작으로 본다.
- **FR-007**: 구독으로 받는 창에는 같은 이벤트를 앱 내부 전달로 보내지 않는다(중복 0). 앱 내부 전달 코드는 지우지 않는다(8단계).
- **FR-008**: 연결이 끊기면 자동으로 다시 연결하고 대상마다 **화면에 반영(전달)을 마친 마지막 지점**부터 이어 받는다(받기만 하고 반영하지 못한 이벤트는 다시 받는다). 재연결 시도는 간격을 늘려 가며 계속하고, 연결 상태를 사용자에게 보인다.
- **FR-009**: 이어 받을 수 없다는 알림을 받으면 사유별로 정해진 복구를 한다 — 대상 재조회, 세대가 바뀌었으면 전체 재조회(작업대 다시 열기 포함). 재조회와 다시 여는 구독 사이 경계에서 변경을 놓치거나 두 번 반영하지 않는다.
- **FR-010**: 변경 조작의 실패는 두 가지로 구분한다. (a) 보내기 전 연결 없음 → 보내지 않고 "적용되지 않음". (b) 보낸 뒤 응답 유실 → "적용 여부 불명". (b)는 같은 서버 세대에서 같은 멱등성 키로 재시도해 저장된 결과를 받고(두 번 적용 없음), 서버가 새 세대면 자동으로 다시 보내지 않는다.
- **FR-011**: 경로 선택은 창이 처음 뜰 때 한 번만 한다 — 끝점을 쓸 수 없거나 연결 정보를 받지 못하면 그 창은 처음부터 오늘 경로로 동작하고 이유를 진단 기록에 남긴다. 네트워크 경로로 시작한 창은 나중에 끊겨도 오늘 경로로 자동 전환하지 않는다. 한 창 안에서 호출과 이벤트는 같은 경로를 쓴다.
- **FR-012**: 화면의 기존 자동 시험은 새 경로에서 같은 기대값으로 통과한다(기대값을 바꿔 맞추지 않는다).
- **FR-013**: 실제 앱에서 창을 열어 연결·호출·구독·재연결이 되는지 자동으로 확인하는 증거를 남긴다(개발 출처와 배포 출처).

### Key Entities

- **연결 정보**: 창이 받는 끝점 주소, 짧은 자격 증명과 만료 시각. 창 출처에 묶인다.
- **창의 작업대**: 세션 창 하나에 대응하는 작업대 id. 창 수명과 같다.
- **구독 대상**: 스트림 id와 화면에 반영을 마친 마지막 순번(과 세대). 재연결 때 이어 받는 기준.
- **연결 상태**: 연결됨·다시 연결 중·끊김(오늘 경로로 전환된 경우 포함). 화면에 보인다.

## Constitution Alignment *(mandatory)*

- **Monorepo boundary**: 대상은 `apps/agentic-workbench`(화면과 Tauri 조립)와 `packages/workbench-client`(AW 전용 공유 클라이언트). `packages/agent-client`(hushline·ask-code 공유)는 바꾸지 않는다. 서버 크레이트는 필요한 조회를 넣을 때만 바꾼다.
- **Frontend layering**: 저장소 모듈은 `entities/*/api`, 연결·구독 수명은 `shared/api`(또는 `app` 조립), 연결 상태 표시는 `widgets`/`features` 규칙을 따른다.
- **Backend boundary**: 창의 작업대 id 제공과 앱 내부 전달 끄기는 inbound(Tauri command)와 infrastructure(데스크톱 전달) 책임이다. 서버 계약은 바꾸지 않는 것이 기본이다.
- **Shared core vs UI**: 공유 클라이언트는 화면 없는 순수 코드다.
- **Persistence and safety**: 새 영속 없음. 자격 증명은 메모리에만 두고 저장하지 않는다.
- **Documentation and Storybook**: `docs/workbench-seam.md`에 화면 전환 절, 연구 문서 진행 각주. 연결 상태 표시를 새로 만들면 Storybook story.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 화면의 서버 소유 호출 중 호환 경로를 쓰는 것이 0개다(데스크톱 표현 상태 목록은 명시적으로 남는다).
- **SC-002**: 화면의 기존 자동 시험이 기대값 변경 없이 모두 통과한다.
- **SC-003**: 구독으로 받는 창에서 같은 이벤트가 두 번 보이는 경우가 0건이다(앱 내부 전달과 구독의 중복 포함).
- **SC-004**: 구독을 강제로 끊고 다시 연결하는 시험 100회 이상(받았지만 반영 전 끊김, 수신자 교체 중 끊김 포함)에서 화면에 빠진 이벤트·중복 반영이 0건이다.
- **SC-004a**: 다른 창의 자격 증명으로 작업대·run·교환·orchestration을 조작·구독하는 시도가 전부 서버 판정으로 거절된다.
- **SC-004b**: 응답을 잃은 변경의 재시도 시험에서 같은 세대는 효과 1회, 새 세대는 자동 재전송 0회다.
- **SC-005**: 실제 앱(개발·배포 출처)에서 창을 열어 프로젝트 조회, run 시작·출력 수신, 연결 강제 종료 뒤 자동 재연결과 이어 받기가 자동 확인된다.
- **SC-006**: 8시간 이상 열어 둔 창에서도 자격 증명 만료로 인한 호출·구독 실패가 0건이다(갱신 시험으로 확인).
- **SC-007**: 끝점 기동을 실패시킨 앱에서 주요 흐름이 오늘 경로로 동작한다.

## Assumptions

- 서버는 이 단계에서도 앱 안에서 뜬다. "서버 재기동(새 세대)"은 자동 시험(가짜 서버·새 세대 흉내)과 앱 재기동으로 확인한다. 별도 프로세스로 떼어 내는 것은 5단계다.
- 세션 창의 작업대는 오늘처럼 앱(데스크톱 조립)이 창 수명에 맞춰 연다. 화면은 앱에서 그 id를 받아 네트워크 호출에 쓴다. 042까지 모든 데스크톱 자격 증명은 같은 주체로 해석되므로, 창 사이 격리(FR-005a)를 위해 창마다 구별되는 주체가 필요하다 — 방식은 plan에서 정한다.
- 호환 command와 앱 내부 전달은 8단계까지 남아 있고, 네트워크 경로를 쓸 수 없는 창의 대체 경로로 쓴다. 한 창 안에서 두 경로를 섞지 않는다.
- 화면 문구·배치는 바꾸지 않는다. 연결 상태 표시는 새로 추가되는 유일한 화면 요소다.
- 계약 생성 도구(OpenAPI → TypeScript)는 037에서 정한 것을 그대로 쓴다.
- Windows 배포 출처 실측, 최종 release 산출물 검증, 독립 서버 수명 검증은 이후 단계의 완료 항목이다.
